# SDD — 도서 검색 성능 실험

> 상태: **동결 (2026-11-04 개발자 확정)**
> 개발 중에는 고치지 않는다.
> 실험 중 나온 결정과 결과는 이 문서가 아니라 `results/`에 남긴다.

## 1. 실험 질문

- 자동완성 → 검색 결과 → 도서 상세 흐름은 어떤 조건에서 느려지는가?
- 어디가 막히는가?
- 무엇을 고치면 얼마나 나아지고, 그 대가는 무엇인가?

## 2. 범위

**포함**

- 자동완성, 검색 결과(필터 · 정렬 · 페이지), 도서 상세 3개 화면 흐름
- 서버 부하 측정과 브라우저 체감 시간 측정
- 상세 페이지의 초기 HTML 확인(크롤러 노출 점검)

**제외**

- 로그인, 구매, 관리자 기능
- 데이터 규모 비교(100만 건으로 고정)
- CDN, 읽기 복제본, 파티셔닝
- OpenSearch 같은 별도 검색엔진
- 저자 링크를 이름으로 풀어내는 작업

## 3. 접근

- 평범하게 구현한 기준선을 태그로 고정한다.
- 조건을 바꿔 가며 기준을 넘는 지점을 찾는다.
- 원인을 근거와 함께 적은 뒤 개선을 1건씩 적용한다.
- 개선은 각각 기준선에서 따로 비교한다.
- 채택한 개선만 마지막에 합쳐 전체 흐름을 다시 측정한다.

## 4. 기술 구성

| 영역 | 선택 |
|---|---|
| 웹 | Next.js (App Router, SSR) |
| DB | PostgreSQL 17 |
| 캐시 | Redis (개선 실험에서만 사용) |
| 실행 | Docker Compose |
| 서버 측정 | k6 |
| 브라우저 측정 | Playwright |

- 측정은 항상 운영 빌드(`next build` + `next start`)로 한다.
- 컨테이너 자원을 고정한다.

| 컨테이너 | CPU | 메모리 |
|---|---|---|
| web | 2 | 2GB |
| db | 2 | 2GB |
| redis | 1 | 512MB |
| k6 | 2 | 1GB |

## 5. 데이터

**실제 데이터**

- 파일: `data/books_1m.jsonl` (100만 건, 커밋 제외)
- 출처: 국립중앙도서관 LOD, 공공누리 제1유형 · CC0 1.0
- 조건과 시드: `data/manifest.json`

**합성 데이터 (시드 고정, 결과에 합성임을 밝힘)**

| 항목 | 만드는 방법 |
|---|---|
| 인기도 | 지프 분포 (α=1.0) |
| 리뷰 | 300만 건, 인기도에 비례 |
| 소장 상태 | 가짜 API, 지연 100ms 고정 |
| 표지 | 생성 이미지 20종, 200~300KB |

- 저자 이름이 없는 약 20%는 화면에 "저자 정보 없음"으로 표시한다.
- 비도서 혼입은 걸러내지 않는다. 품질 평가 검색어 세트에서만 피한다.

**테이블**

```sql
books (
  id text primary key,
  title text not null,
  subtitle text,
  publisher text,
  year int,
  kdc text,
  series text,
  volume text,
  description text,
  toc text,
  keywords text[],
  isbn text[],
  popularity int not null
)
authors (id bigserial primary key, name text unique not null)
book_authors (
  book_id text references books,
  author_id bigint references authors,
  position int,
  primary key (book_id, author_id)
)
reviews (
  id bigserial primary key,
  book_id text references books,
  rating int not null,
  body text not null,
  created_at timestamptz not null
)
```

- 기준선 인덱스: 기본 키, 유니크, `book_authors(author_id)`, `reviews(book_id)`
- 그 외 인덱스는 개선 실험에서 추가한다.

## 6. 기준선 구현

일부러 느리게 만들지 않는다. 처음 만들 때 흔히 쓰는 방식으로 구현한다.

| API | 기준선 방식 |
|---|---|
| `GET /api/autocomplete?q=` | 제목 · 저자 `ILIKE 'q%'`, 10개 |
| `GET /api/search` | 제목 · 저자 `ILIKE '%q%'`, OFFSET |
| `GET /api/books/:id` | 기본 키 조회 + 저자 조인 |
| `GET /api/books/:id/reviews` | 최신 20건 + 평균 · 개수 집계 |
| `GET /api/books/:id/recommendations` | 같은 대분류 인기순 6건 |
| `GET /api/books/:id/holding` | 가짜 소장 상태 API |

- **검색 파라미터:** `q`, `kdc`, `sort`(관련순 · 인기순 · 최신순), `page`
- **검색 응답:** 20건 + 전체 개수(`COUNT(*)`)
- **자동완성 프론트:** 입력할 때마다 요청한다. 디바운스와 요청 취소는 없다.
- **자동완성 입력:** 한글 조합 중 입력은 기준선부터 처리해서 기능 버그를 막는다.
- **상세 페이지:** SSR에서 도서, 리뷰, 추천, 소장 상태를 순서대로 조회한 뒤 HTML을 보낸다.
- **이미지:** 원본 그대로 쓴다.

## 7. 합격 기준

| 항목 | 기준 |
|---|---|
| 자동완성 API | p95 100ms 이하 |
| 검색 API | p95 500ms 이하 |
| 상세 API | p95 300ms 이하 |
| 클릭 → 상세 핵심 내용 | p95 1초 이하 |
| 에러율 | 1% 미만 |

- 기준선 측정 결과를 본 뒤에도 기준은 바꾸지 않는다.

## 8. 측정 조건

**바꾸는 축**

| 축 | 값 |
|---|---|
| 부하 | 10 · 50 · 200 RPS |
| 캐시 상태 | 비어 있음 · 채워짐 |
| 네트워크 | 제한 없음 · 느린 모바일 |

**검색어 묶음 (`bench/queries.json`, 시드 고정)**

| 묶음 | 예 | 트래픽 |
|---|---|---|
| 결과 많음 | 연구, 한국, 사랑 | 50% |
| 결과 적음 | 파이썬, 해리 | 30% |
| 저자명 | 김지영 | 10% |
| 한 글자 | 꽃 | 5% |
| 결과 없음 | 고정 무의미 문자열 | 5% |

- 검색 조건은 검색만, 필터 추가, 정렬 추가, 깊은 페이지(page=5000)로 나눈다.
- 자동완성은 글자를 하나씩 입력하는 순서대로 요청을 만든다.
- 상세는 인기도 분포를 따라 도서를 고른다.

**실행 규칙**

- 조건마다 3번 측정한다. 1번은 예열 30초 + 측정 2분이다.
- 측정 사이에 컨테이너를 다시 시작하고, 시드 데이터는 그대로 둔다.
- 다른 무거운 작업은 멈춘다.
- 3번으로는 우연을 다 가리지 못한다는 한계를 결과에 적는다.

**수집 지표**

- 서버: p50 · p95 · p99, 에러율, 처리량
- DB: 슬로우 쿼리, `pg_stat_statements`, 실행 계획, 커넥션 대기
- 브라우저: 입력 → 후보 표시, 검색 → 결과 표시, 클릭 → 핵심 내용 표시
- SPA 이동은 `performance.mark`로 잰다.

## 9. 가설과 개선 후보

측정 전에 예상을 적어 두고, 결과와 비교한다.

| ID | 가설 원인 | 개선 | 대가 |
|---|---|---|---|
| A1 | 입력마다 요청 | 디바운스 + 요청 취소 | 표시 지연 |
| A2 | 접두어 인덱스 없음 | `text_pattern_ops` 인덱스 | 쓰기 비용 |
| A3 | DB 직접 조회 | Redis 사전 계산 후보 | 갱신 지연 |
| S1 | 전체 스캔 | `pg_trgm` GIN | 인덱스 크기 |
| S2 | OFFSET 비용 | 커서 페이지네이션 | 페이지 이동 |
| S3 | COUNT 비용 | 개수 생략 · 근사 | 정확도 |
| S4 | 필터 · 정렬 불일치 | 복합 인덱스 | 쓰기 비용 |
| S5 | 인기어 중복 계산 | Redis 캐시 | 오래된 결과 |
| D1 | 빈 화면 대기 | 목록 데이터 먼저 표시 | 값 불일치 |
| D2 | 이동 후 조회 | 프리페치 | 요청 증가 |
| D3 | 순차 호출 | 병렬 호출 | 복잡도 |
| D4 | SSR 전체 대기 | 스트리밍 + 지연 로딩 | HTML 누락 위험 |
| D5 | 리뷰 집계 비용 | 집계값 저장 | 정합성 |
| D6 | 큰 이미지 | 크기 조정 · 지연 로딩 | 변환 비용 |

**한글 검색 품질 개선**

| ID | 문제 | 개선 |
|---|---|---|
| Q1 | "해리 포터" · "해리포터" | 공백 제거 컬럼 |
| Q2 | 초성 검색 불가 | 초성 컬럼 |

**각 개선에서 비교할 부작용**

- 인덱스와 Redis가 차지하는 크기
- 시드 입력 시간 변화
- 검색 품질 변화
- 총 요청 수 변화
- 데이터가 바뀐 뒤 화면에 반영되기까지의 시간
- 상세 초기 HTML에 핵심 내용이 남아 있는지

**검색 품질 평가**

- 기대 결과를 정해 둔 검색어 30개를 `bench/quality.json`에 고정한다.
- 비도서가 답이 되지 않게 고르고, 상위 20건 안에 기대 결과가 있는 비율을 본다.

## 10. 에이전트 구성

| 담당 | 하는 일 | 쓰기 범위 |
|---|---|---|
| 개발자 | 기준 승인, 결과 판단 | 전체 |
| 조율 | 순서 관리, 결과 정리 | `results/` |
| 구현 | 기준선, 개선 1건 구현 | `app/`, `db/` |
| 분석 | 로그, 실행 계획 분석 | `results/` 분석 글 |
| 검증 | 수치, 부작용 확인 | `results/` 검증 글 |
| 측정 스크립트 | k6, Playwright 실행 | `results/raw/` |

- **측정 코드 보호:** 구현 에이전트는 `bench/`를 바꾸지 않는다.
- **측정 코드 검사:** 측정 전에 `bench/` 체크섬이 기준선과 같은지 스크립트로 확인한다.
- **수치 출처:** 결과 문서의 수치는 `results/raw/`에서 계산한다. 에이전트가 직접 적지 않는다.
- **모델:** 구현 · 검증은 Sonnet 5.5, 분석은 막힐 때만 Opus 5.5를 쓴다.
- **실행 전 확인:** `claude -p`를 쓰면 `claude auth status`로 구독 로그인을 확인한다.
- **기록:** 개선마다 시간, 턴 수, 변경 파일 수, 환산 비용을 남긴다.

## 11. 진행 순서

1. 데이터 입력: 스키마, 시드, 합성 데이터
2. 측정 도구: `bench/` 작성 후 빈 앱으로 동작 확인
3. 기준선 구현과 기능 테스트, 태그 `baseline`
4. 기준선 측정과 느린 지점 정리
5. 개발자 확인: 측정할 개선 후보 선택
6. 개선별 실험: `baseline`에서 브랜치 생성 → 구현 → 측정 → 분석 → 검증 → 개발자 판단
7. 채택한 개선을 합쳐 전체 흐름 재측정
8. 결과 문서 작성

- 개선 1건의 측정은 약 25분(3개 부하 × 3번)으로 예상한다.
- 개선 16건을 모두 하면 측정만 약 7시간이다. 5단계에서 후보를 줄일 수 있다.

## 13. 대안과 고르지 않은 이유

| 대안 | 고르지 않은 이유 |
|---|---|
| 처음부터 OpenSearch | 기본기 효과가 가려짐 |
| 합성 도서 데이터 | 실제 분포가 사라짐 |
| 데이터 규모 비교 | 100만 건으로 결정 |
| 개선 누적 적용 | 개별 효과 구분 불가 |
| 에이전트가 직접 측정 | 측정 방법이 흔들림 |

## 14. 위험

- **메모리 상주:** 100만 건은 DB 메모리에 대부분 올라갈 수 있다. 디스크 병목은 재현되지 않을 수 있다.
- **같은 장비:** k6와 앱이 같은 장비에서 돌아 200 RPS에서 서로 영향을 줄 수 있다.
- **로컬 네트워크:** 실제 지연이 없어서 서버 쪽 차이가 작게 보일 수 있다. 느린 모바일 조건으로 일부 보완한다.
- **Docker 환경:** macOS Docker의 파일 입출력은 실제 서버와 다르다. 절대값보다 전후 비교로 해석한다.
- **합성 데이터:** 리뷰와 인기도 분포가 결과에 영향을 준다. 해당 결과는 합성 기반으로 표시한다.
- **원본 재현:** 원본을 지운 뒤에는 추출을 재현하기 어렵다. `books_1m.jsonl`을 별도로 보관한다.

## 15. 완료 판정

- 기준선이 기능 테스트를 통과한다.
- 모든 측정에서 `bench/` 체크섬이 같다.
- 결과 문서의 수치가 `results/raw/`와 일치한다.
- 각 개선에 효과와 부작용, 개발자 판단이 적혀 있다.
- 채택 조합의 전체 흐름 측정 결과가 있다.
- 합성 데이터와 측정하지 않은 범위가 결과에 밝혀져 있다.
