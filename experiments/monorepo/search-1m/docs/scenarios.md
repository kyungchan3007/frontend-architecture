# 느린 이유별 대응 시나리오

> 상태: **확정 (2026-11-04 개발자 확정)**
> 있을 법한 상황을 재현하고, 원인 확인 · 대처 · 해결 확인을 정리한다.

## 먼저 나누기: 프론트인가, 백엔드인가

| 확인 값 | 결과 | 먼저 볼 곳 |
|---|---|---|
| 서버 응답 대기(TTFB) | 김 | 백엔드 |
| TTFB 이후 표시까지 | 김 | 프론트 |
| 사용자당 요청 수 | 많음 | 프론트 |
| 혼자 써도 느림 | 예 | 쿼리, 렌더링 |
| 몰릴 때만 느림 | 예 | 백엔드 자원 |

- 증상이 나타난 곳과 원인이 있는 곳은 다를 수 있다.
- 예를 들어 자동완성 요청 폭주는 서버가 밀리지만 원인은 프론트다.

## 양쪽이 함께 푸는 경우

- **B9 + F6:** 외부 API가 느려도 핵심 내용을 먼저 보여 준다.
- **B4 + F1:** 요청 수를 줄이고 서버 쿼리도 줄인다.
- **B1 + F1:** 자동완성 쿼리와 요청 빈도를 함께 다룬다.

## 시나리오마다 정리할 항목

- **담당:** 프론트, 백엔드, 양쪽
- **재현:** 어떤 상황을 어떻게 만들었나
- **증상:** 사용자에게 어떻게 보이나
- **구분:** 프론트와 백엔드를 어떤 값으로 구분했나
- **원인 확인:** 어떤 도구의 어떤 값으로 확정했나
- **대처:** 무엇을 바꿨나
- **해결 확인:** 어떤 값이 어떻게 바뀌었나
- **대가:** 고치면서 잃은 것

## 재현 방식

- 시나리오마다 `baseline`에서 브랜치를 만든다.
- B1, B2, B3, B4, F1, F2, B9는 기준선에 이미 있는 동작으로 재현한다.
- 나머지는 브랜치에서 상황을 일부러 만든다.
- 측정은 전후 1번씩 한다. 흔들림이 커서 판단이 안 될 때만 다시 측정한다.
